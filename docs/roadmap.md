# SpiceSibyl Roadmap

## Phase 1 ✓
- Monorepo scaffold
- FastAPI OpenAI-compatible mock API
- Angular chat shell
- Docker Compose

## Phase 2 ✓
- LiteLLM real provider routing (Ollama, Groq, Mistral, Together, Fireworks, HuggingFace)
- Streaming UI via SSE
- Provider management page (GET /providers, POST /providers/{id}/test)
- GeminiProvider — dedicated adapter for Google Generative AI
- Cerebras + Mistral providers (direct HTTP, no LiteLLM)
- Model discovery endpoints × 6 (Cloudflare, OpenRouter, Gemini, Groq, Cerebras, Mistral)
- Global toast notification system (ErrorInterceptor + NotificationService + ToastContainerComponent)
- Structured SSE error propagation (event: error frame from backend → toast + bubble message)
- HTTP 429 mapping for rate-limit errors

## Phase 3 ✓
- **Conversation persistence** — SQLite via aiosqlite; full message history with telemetry saved after each exchange; sidebar conversation list with create/delete
- **API key vaulting** — Fernet (AES-128-CBC + HMAC-SHA256) encryption; keys stored in SQLite; in-memory cache; vault→env fallback in all providers; PUT + DELETE /providers/{id}/key
- **Profile system** — named local profiles (no passwords); profile UUID stored in localStorage; per-profile conversation history; profile selector modal on first visit; profile switcher in sidebar

## Phase 4 ✓
- **Telegram bot** — polling-based; per-chat conversation history; streaming replies with live edit; `/start`, `/new`, `/model`, `/models`; optional user allowlist (`TELEGRAM_ALLOWED_USERS`)

## Phase 5 ✓
- **Usage telemetry** — per-message token counts + latency; provider-reported cost estimates
- **Usage stats / cost tracking dashboard** — GET /v1/stats (by profile or global); Angular `/stats` page with summary cards + per-provider / per-model tables
- **Tool calling** — server-side tool execution loop (max 5 iterations); 3 built-in tools (get_datetime, calculator, web_search via DuckDuckGo); GET /v1/tools; SSE tool_call/tool_result events; toggle ON/OFF in sidebar; tool bubbles in chat
- **Conversation search / full-text index** — SQLite FTS5 with sync triggers; GET /v1/conversations/search?q=; search bar in sidebar with 300 ms debounce, inline results with snippets, Escape to close
- **Multi-MCP orchestrator (agent mode)** — OrchestratorProvider routes `agent/*` models to an external sidecar; Telegram `/agent` and `/chat` commands to toggle modes
- **NVIDIA and Ollama model discovery** — live model catalog fetch for NVIDIA and Ollama providers

## Phase 6 ✓
- **System prompt** — persistent system instructions stored in localStorage; collapsible sidebar section; save/clear actions
- **Model parameters** — temperature slider (0–2) and max tokens input exposed in the sidebar; sent with every completion request
- **Conversation export** — GET /conversations/{id}/export?format=md|json; download buttons in the topbar (Markdown and JSON)
- **Message actions** — copy message to clipboard, regenerate last assistant response, edit last user message; hover-to-reveal action buttons on every message
- **Voice input** — Web Speech API integration; microphone button in the composer with visual pulse animation while listening
- **Stream cancellation** — stop button replaces the send button during streaming; aborts the in-flight request and resets the UI
- **Syntax highlighting** — highlight.js integration for code blocks in assistant responses; language-aware rendering via custom marked renderer
- **`read_url` tool** — new built-in tool that fetches a web page and returns plain-text content (HTML stripped); up to 4 000 chars; registered in the tool registry
- **Improved `web_search`** — primary strategy switched to DuckDuckGo HTML scraping for richer snippets; falls back to the instant-answer JSON API
- **Real provider connectivity test** — POST /providers/{id}/test now sends a minimal completion request to cloud providers instead of only checking key presence
- **Database performance indexes** — added indexes on messages(conversation_id), conversations(profile_id), conversations(updated_at), messages(provider), messages(role)
- **Hardened error handling** — bare `except Exception` replaced with specific exception types across chat service, tools, and providers; improved logging levels (debug for normal ops, warning for failures)
- **Vault security warning** — startup logs a SECURITY warning when VAULT_SECRET_KEY is still set to the default placeholder

## Phase 7 ✓
- **Image-to-text (vision)** — upload images in the web chat (click, drag, paste) or send photos to the Telegram bot; images are base64-encoded and forwarded as OpenAI-compatible multipart content to any vision-capable model (Gemini, Groq/Llama-4-Scout, etc.)
- **Text-to-image generation** — `/imagine <prompt>` command in both web UI and Telegram; configurable provider fallback chain via `IMAGE_GENERATION_CHAIN` env var (format: `provider:model,...`); supported providers: Gemini (Imagen / Flash Image), Hugging Face (FLUX.1-schnell), Cloudflare Workers AI (SDXL), Together AI (FLUX.1-schnell-Free)
- **Image generation endpoint** — `POST /v1/images/generations` with automatic provider fallback; each entry in the chain is tried in order, skipping unconfigured providers and falling back on errors
- **Telegram `/imagine`** — generates an image and sends it as a Telegram photo with provider/model caption
- **Telegram photo handler** — photos sent to the bot are automatically described by the active model via vision

- **Environment documentation** — deployment guide (`docs/deploy.md`) rewritten with `PUBLIC_URL`, `VAULT_SECRET_KEY`, DDNS setup, TLS options, and architecture diagram

## Phase 13 — Security & access ✓
- **Authentication and access control** — user accounts with email/password login (bcrypt hashing); role-based permissions (`admin`, `user`, `read-only`); JWT access tokens (30 min) + rotating refresh tokens (14 d) tracked in `refresh_tokens` for revocation. Auth is **mandatory** on all `/api/v1` routes except the public allowlist (`/auth/*`, `/health`, `GET /shared/{token}`). A bootstrap admin is created on first boot from `ADMIN_EMAIL`/`ADMIN_PASSWORD`, adopting any pre-auth ("orphan") profiles. Each user owns N profiles (`profiles.user_id`); every profile-scoped endpoint validates ownership via the `resolve_profile` dependency so data is isolated per user. Frontend: `AuthService` + `authInterceptor` (Bearer + silent refresh on 401) + `authGuard`, a `/login` page, and a navbar user chip with logout. (OAuth deferred to a later phase.)
- **Rate limiting** — per-user sliding-window limiter (`RATE_LIMIT_DEFAULT`, default `60/minute`) keyed by the authenticated user id (correct behind the nginx proxy); HTTP 429 with `Retry-After` header. In-memory (single-process) — a shared store is noted for Phase 16 multi-worker deployments.
- **Audit log** — `audit_log` table records who did what and when (logins, conversation/profile deletions, provider key updates, user role/disable changes) with the client IP; viewable by admins via `GET /v1/auth/audit`.

## Phase 14 — Knowledge & RAG ✓
- **RAG / document ingestion** — upload documents (PDF, TXT, DOCX, Markdown) to a per-profile knowledge base; text is extracted, chunked (800 chars / 120 overlap), embedded via a provider fallback chain (`EMBEDDING_CHAIN`: Ollama `nomic-embed-text` → Gemini → Mistral) and stored as float32 BLOB vectors in SQLite (`kb_documents` / `kb_chunks`). `GET/POST/DELETE /v1/knowledge/documents` + `POST /v1/knowledge/search`. At query time, when `rag:true` is set, the top-k chunks (cosine similarity in numpy) are folded into the last user message and the sources are streamed back as an SSE `rag_context` frame. Web UI: "Knowledge base" sidebar panel with upload/list/delete, a RAG ON/OFF toggle, and citation chips under each grounded reply
- **Telegram scheduled reminders** — `/remind 15:50 Check backups` (absolute `HH:MM` or relative `+30m` / `2h` / `1d`); persisted in `telegram_reminders` and scheduled on the PTB `JobQueue` (requires the `python-telegram-bot[job-queue]` extra), so they survive a restart (reloaded on boot). `/reminders` lists pending, `/unremind <id>` cancels. Times use the configurable `TIMEZONE` (default `Europe/Rome`) regardless of the container's system clock
- **Telegram multi-language support** — `/lang` (inline keyboard) or `/lang en|it` switches the bot's UI language per chat; locale persisted in `telegram_prefs` and warm-cached at boot. Strings live in `app/telegram/i18n.py` (`it` default, `en`); `t(locale, key)` with fallback to the default locale

## Phase 16 — Observability & ops ✓
*Priority 1 — foundational, low-risk, high operational value; unblocks confident iteration on everything below.*
- **Health & readiness endpoints** — `GET /api/v1/health` (liveness, stable contract for the Dockerfile HEALTHCHECK) and `GET /api/v1/ready` (verifies DB connectivity + at least one configured provider, returns 503 when degraded); compose now defines explicit backend healthchecks and nginx/certbot `depends_on: condition: service_healthy`
- **Prometheus metrics** — `GET /api/v1/metrics` (OpenMetrics) exposing `sibyl_http_requests_total`/`_duration_seconds`, per-provider `sibyl_provider_requests_total`, `sibyl_provider_tokens_total{kind}`, `sibyl_provider_latency_seconds`, and `sibyl_active_sse_streams`; optional `METRICS_TOKEN` bearer guard; Grafana dashboard JSON in `docs/grafana-dashboard.json`
- **Structured logging with request correlation** — `LOG_FORMAT=json` enables JSON logs carrying a `request_id` (ContextVar) generated by `RequestContextMiddleware` (reuses inbound `X-Request-ID`, echoes it on the response); propagated to the Multi-MCP sidecar via header and bound in Telegram flows for end-to-end tracing
- **Automatic provider fallback for chat completions** — `CHAT_FALLBACK_CHAIN` (same `provider:model` format as the image/embedding chains); when a provider errors/times out **before** emitting any output the gateway transparently retries the next configured provider and emits an SSE `provider_switch` frame, surfaced as a notice in the web UI; once tokens have streamed the error is propagated (no duplicate output)
- **Scheduled DB backup & restore** — opt-in background task (`BACKUP_ENABLED`, interval + retention) snapshots SQLite via the online backup API to `BACKUP_DIR` on a mounted volume; admin endpoints `POST /v1/admin/backup`, `GET /v1/admin/backups`, `POST /v1/admin/restore`, plus per-profile `GET /v1/admin/export` / `POST /v1/admin/import` (conversations, messages, KB, templates, tags) as a single zip archive; all recorded in the audit log
- **Admin Ops page** — admin-only `/ops` page (navbar entry gated on the `admin` role, `adminGuard`) surfacing live readiness (DB + provider count + active SSE streams parsed from `/metrics`), a link to raw `/metrics`, backup management (list / create / restore), and per-profile export/import

## Phase 17 — Advanced RAG (extends Phase 14) ✓
*Priority 2 — builds directly on the shipped knowledge base; biggest answer-quality gain once observability is in place.*
- **Hybrid search + reranking** — retrieval now fuses an FTS5 lexical arm (`kb_chunks_fts`, bm25-ranked) with the vector-similarity arm via Reciprocal Rank Fusion (`RAG_HYBRID`, `RAG_CANDIDATE_POOL`); an opt-in reranker (`RAG_RERANK=llm` + `RAG_RERANK_MODEL`) reorders the fused candidate pool with an LLM before context injection, degrading gracefully to fused order on any error
- **Web & URL ingestion** — `POST /v1/knowledge/urls` fetches a web page (full-text HTML extraction, reusing the `read_url` approach), then chunks/embeds/indexes it like an upload; documents carry `source_type`/`source_url` and are flagged 🔗 in the UI with a URL input in the Knowledge sidebar panel
- **Inline source highlighting** — every chunk stores its `char_start`/`char_end` span within the document's full `source_text`; `RagSource` carries the offsets and `GET /v1/knowledge/documents/{id}/source` exposes the source text so citation chips can deep-link to the exact passage
- **KB management UX** — `GET /documents/{id}/chunks` (per-document chunk preview), `POST /documents/{id}/reembed` (re-chunk + re-embed from stored source text after an `EMBEDDING_CHAIN` change — re-embed button in the UI), and per-conversation KB scoping via `document_ids` on `/search` and `rag_document_ids` on chat completions
- **Dedicated vector store** — *deferred*: retrieval still uses the numpy cosine scan (now only the vector arm of hybrid search); `sqlite-vec` remains the documented single-file upgrade path for very large corpora

## Phase 18 — Agent & tooling avanzato ✓
*Priority 3 — high-leverage extensibility; depends on solid logging/metrics (Phase 16) to debug multi-step runs. Usage guide with worked examples: [phase-18-usage.md](phase-18-usage.md).*
- **User-defined custom tools** ✓ — HTTP-backed tools registered from the UI (name, description, JSON-schema parameters, endpoint URL/method/headers + none/bearer/custom-header auth, timeout) without code changes; stored per profile in `custom_tools` and injected into the chat tool loop namespaced `custom__<name>` (merged into `GET /v1/tools`, routed by `execute_tool` with the request's profile). Arguments are delivered as the JSON body (POST/PUT/PATCH) or query params (GET); the response body is the tool result. CRUD + one-shot test endpoints under `/v1/tools/custom` (audited); `/tools` page with create/edit form, enable toggle, and an inline test panel
- **MCP server management UI** ✓ — MCP servers are configured in the standard `mcpServers` JSON shape (`command`/`args`/`env`/`cwd`) and stored in a dedicated `mcp_servers` table (admin-managed, global). Admin endpoints `GET/POST /v1/mcp/servers`, `PATCH`/`DELETE /v1/mcp/servers/{id}` (enable/disable/remove), `POST /v1/mcp/servers/{id}/test`, `POST /v1/mcp/reload`, and standard-format `GET /v1/mcp/config` / `POST /v1/mcp/import` (all audited). A minimal stdio JSON-RPC MCP client (`mcp_client`, no SDK dep — 3.9-compatible) spawns each enabled server, performs the `initialize` handshake and `tools/list`/`tools/call`; the manager (`mcp_service`) probes health, caches discovery, and injects the discovered tools into the chat tool-loop namespaced `mcp__<server>__<tool>` (merged into `GET /v1/tools`, routed by `execute_tool`). Admin-only `/mcp` page: paste/import a bundle, enable/disable toggle, per-server health + tool discovery, test, export `mcp.json`
- **Persistent multi-step workflows** ✓ — durable agent runs (`agent_runs` + `agent_run_steps`): a background server-side tool loop works towards a goal with the full tool registry (built-ins, MCP, custom) for up to `WORKFLOW_DEFAULT_MAX_STEPS`/`WORKFLOW_MAX_STEPS_LIMIT` iterations, well beyond the 5-iteration chat loop. Every assistant turn / tool call / tool result is persisted as an inspectable step and the serialized message history is checkpointed after each iteration, so runs pause/resume losslessly — including across restarts (stale `running` runs are reconciled to `paused`). Endpoints under `/v1/workflows` (create/list/detail/pause/resume/cancel/delete, audited); `/workflows` page with create form (model picker, max steps, extra instructions), status badges, pause/resume/cancel, and an auto-refreshing step timeline
- **Sandboxed code interpreter** ✓ — `python_exec` built-in tool: isolated `python -I` subprocess with rlimits (CPU seconds, memory `CODE_INTERPRETER_MEMORY_MB`, file size, fd/process counts), wall-clock timeout (`CODE_INTERPRETER_TIMEOUT`, killed process group), a minimal env, and Python-level socket stubbing (no network); ephemeral working directory with file in/out — input `files` are materialised before the run, created files are reported (small text files inline) and everything is deleted afterwards. Opt-out via `CODE_INTERPRETER_ENABLED=false`

## Phase 19 — Personalization & quality ✓
*Priority 4 — quality-of-life and cost wins that layer cleanly on the stack above.*
- **19.a — Per-profile persistent memory** ✓ — facts about the user remembered across conversations, stored in a `profile_memories` table (content, category `preference|fact|project|instruction`, `source_conversation_id`, `enabled`). Auto-extraction: after each persisted exchange an async low-cost LLM call (`MEMORY_EXTRACTION_MODEL`, default = `DEFAULT_MODEL`) receives the latest messages + existing memories and returns `add`/`update`/`delete` operations (dedup, `MEMORY_MAX_ITEMS` cap). Injection: when ON, enabled memories are compacted into a `<user_memory>` block appended to the system prompt (`MEMORY_MAX_CHARS` budget, most-recent first). Three-level toggle: per-profile `memory_enabled` (OFF = no extraction, no injection), per-request `memory:false` flag (incognito chat, mirrors `rag:true`), and per-memory `enabled` flag. `/v1/memories` CRUD + settings endpoints; SSE `memory_context` frame. UI: "Memoria" sidebar panel (list/toggle/delete, manual add, forget-all, profile switch) + 🧠 transparency chip on memory-grounded replies; Telegram `/memory on|off|list|del <id>` persisted in `telegram_prefs` with injection/extraction in `_stream_reply` for linked profiles. Plain injection (no vector retrieval) — top-k retrieval via `rag_service` noted as a later upgrade if memories grow large
- **19.b — LLM auto-titling** ✓ — a background task after the first persisted exchange generates a concise title (`TITLE_MODEL`, opt-out `AUTO_TITLE_ENABLED=false`), replacing the first-60-chars heuristic; the sidebar refreshes to pick it up
- **19.c — Response cache** ✓ — exact-match in-memory LRU cache of completed replies (`RESPONSE_CACHE_ENABLED`, TTL + max-entries settings) keyed on model/messages/params; hits skip the provider and replay as a single chunk flagged `cached` (⚡ chip). Tools, `agent/*` and multimodal requests are never cached. *Provider-side prompt caching deferred*
- **19.d — Feedback & evaluation** ✓ — 👍/👎 with optional notes on assistant messages (`rating`/`feedback_note` columns; `PUT`/`DELETE /v1/feedback/messages/{id}`, `/stats`); exportable dataset (`GET /v1/feedback/export`, each rated reply paired with its prompt) and a lightweight regression harness (`backend/scripts/eval_regression.py`) over saved prompts
- **19.e — Built-in tools expansion** ✓ — 8 new tools in the registry alongside `get_datetime`/`calculator`/`web_search`/`read_url`/`python_exec`:
  - `kb_search` ✓ — agentic RAG: query the profile's knowledge base via `rag_service.retrieve`, letting the model decide when to consult documents instead of always injecting context
  - `search_conversations` ✓ — episodic memory: full-text search over past conversations reusing the existing FTS5 index
  - `generate_image` ✓ — the image-generation chain as a tool so the agent can produce images mid-reasoning (the model context gets a short placeholder; the UI gets the image)
  - `get_weather` ✓ — current weather + forecast via Open-Meteo (free, no API key)
  - `fetch_rss` ✓ — fetch an RSS/Atom feed and return the latest N entries; combined with Telegram reminders enables "summarize the news every morning"
  - `create_reminder` ✓ — natural-language access to Phase 14 Telegram reminders via the linked profile; live-scheduled on the running bot JobQueue
  - `extract_document` ✓ — read a PDF/DOCX/TXT/MD from a URL using the existing extractors, without KB ingestion
  - `http_request` ✓ — generic HTTP call (GET/POST, sanitized headers, `HTTP_REQUEST_ALLOWED_DOMAINS` allowlist) with SSRF hardening (private/loopback IPs blocked — now applied to `read_url` too)

## Phase 20 — Collaboration ✓ (no 20.c)
*Priority 5 — highest-value but gated on Phase 13 auth/accounts; sequenced last.*
- **20.a — Shared workspaces** ✓ — team-scoped workspaces (`workspaces` + `workspace_members`) owned by a user, with role-based access (`owner` > `admin` > `editor` > `viewer`). Members are invited by email; conversations and knowledge base documents (owned by an individual profile) are *shared into* a workspace via join tables (`workspace_conversations` / `workspace_documents`), making them visible to every member. `GET/POST/PATCH/DELETE /v1/workspaces` + `/{ws}/members`, `/{ws}/conversations`, `/{ws}/documents`; sharing requires editor+ and ownership of the resource, membership management requires admin+, deletion is owner-only, and any member may self-leave. Web UI: "Workspace" page with a workspace list/create sidebar and a detail pane for members (invite/role/remove) and shared conversations/documents (builds on Phase 13 accounts and Phase 17 KB scoping)
- **20.b — Annotations & comments** ✓ — threaded comments on shared conversations (`comments` table, `parent_id` threading, `message_id` for per-message anchoring; soft-deleted so replies keep their anchor). Access mirrors conversation reach — the owner or any member of a workspace it is shared into can read/post, while editing/deleting is restricted to the comment's author. `GET/POST/PATCH/DELETE /v1/conversations/{id}/comments`. Web UI: a collapsible threaded comment panel under each shared conversation in the Workspace page (post / reply / edit / delete own)
- **20.c — Real-time collaboration** — multiple users in one conversation over WebSocket, with presence indicators and live-streaming of in-flight responses to all participants

## Phase 21 — Telegram knowledge base ✓ (a–c; 21.d folded into Phase 23.c)
*Extends Phase 14/17 RAG to the Telegram channel; requires a linked web profile (`/link`).*
- **21.a — `/kb` document ingestion** ✓ — send a PDF/TXT/DOCX/MD document with a `/kb` caption to ingest it into the linked profile's knowledge base (`_ingest_document_to_kb` → `kb_repository.create_document` + `rag_service.ingest`, same extraction/chunking/embedding as web uploads, with sha256 byte-hash duplicate detection); `/kb list` shows documents with a status icon (✅/⏳/⚠️), 🔗 for URL-sourced docs, and chunk count, `/kb del <id>` removes one by id prefix
- **21.b — `/rag on|off`** ✓ — per-chat toggle (persisted in `telegram_prefs.rag`, OFF by default, warm-cached at boot via `_load_rag_prefs` like the locale); when ON, `_stream_reply` retrieves top-k chunks via `rag_service.retrieve` and folds `build_context_block` into the last user message (mirroring `ChatService._apply_rag`), appending a 📚 sources footer (deduped filenames) to the reply
- **21.c — Unlinked fallback** ✓ — `/kb list|del`, `/rag on`, and `/kb`-captioned uploads prompt for `/link` when no web profile is linked; documents sent without the `/kb` caption keep the existing one-shot context behaviour
- **21.d — cross notifications** — *folded into Phase 23.c* (Cross-channel notifications UI ↔ Telegram): a single event bridge covering web→Telegram (and Telegram→web) for linked users, rather than a separate one-directional path here

## Phase 28 — wikillm: enhanced knowledge base (MarkItDown + knowledge graph + sqlite-vec) ✓ (Phase 1)
*Clean replacement of the Phase 14/17 chunk-only KB: structure-aware ingestion, a per-document wiki and a searchable knowledge graph, on a scalable vector store. Phase 1 (structural graph, LLM-free) is shipped; Phase 2 (GraphRAG) layers on the same schema.*
- **28.a — MarkItDown ingestion** ✓ — `document_converter.py` wraps Microsoft **MarkItDown**, converting uploads (PDF, DOCX, PPTX, XLSX, CSV, HTML, EPUB, JSON, XML, TXT/MD) to structured **Markdown** that becomes the document's canonical source (`kb_documents.markdown`). - **28.c — Wiki + knowledge graph** ✓ — `wiki_service.py` builds a per-document section tree (`kb_wiki_pages`, extractive summaries) from the same Markdown; `graph_service.py` (LLM-free) extracts entities (Markdown links, headings, capitalised-phrase frequency), creating `document`/`entity` nodes and `mentions` edges (`kb_graph_nodes`/`kb_graph_edges`) plus chunk↔entity links (`kb_chunk_entities`). ## Phase 29 — Visual node-graph workflow engine (n8n-style) ✓
*The Phase 18 workflow is **agent goal-based**: an LLM iterates over the full tool registry until it hits a final answer or `max_steps` — autonomous but non-deterministic, with no explicit graph. This phase adds a **deterministic DAG-of-typed-nodes** engine (trigger → nodes → connections, per-node data mapping) that runs **alongside** the agent engine rather than replacing it: the existing agent run becomes just one node type (`llm.agent`). Deliberately reuses the durable execution model of `workflow_service.py` (checkpoint after every unit, `status` re-read between units for pause/cancel, `reconcile` after a mid-run restart, `_tasks` asyncio registry), the whole tool registry (built-in + MCP + custom → free "action" nodes), the `reminder_service` polling loop + `reminder_parsing` cron/RRULE/NL (→ schedule triggers, absorbs Phase 27), the Phase 23.c notification bridge (→ delivery nodes), the SSE stream pattern (→ live run view) and the Phase 24 examples gallery (→ importable `graph_json`). `graph_json` (`{nodes:[...], edges:[...]}`) is the source of truth; the visual canvas is layered on last so the engine is testable end-to-end via JSON import with no UI.*

- **29.a — DAG engine + expression resolver + REST (no UI)** ✓ — new tables (same SQLite): `workflows` (`id`, `profile_id`, `name`, `description`, `graph_json`, `active`, `version`, `created_at`), `workflow_versions` (immutable history), `workflow_runs` (evolves from `agent_runs`: `status`, `trigger_type`, `graph_json` snapshot, `context_json`), `workflow_node_runs` (evolves from `agent_run_steps`: `node_id`, `node_type`, `input_json`, `output_json`, `error`, timing), `workflow_triggers` (`type` manual|schedule|webhook|event, `config_json`, `token`, `next_run_at`, `enabled`). `workflow_graph_service.py` runs a **topological scheduler** in waves: each ready node (all incoming edges resolved, ≥1 live) → resolve params → execute → persist `node_run` → checkpoint the run context → activate output handles and propagate to successors; independent ready nodes run in parallel via `asyncio.gather`; nodes with no live input are recorded `skipped`; per-node `retry`/`backoff` + `continueOnFail`. Node kinds shipped: `manual` trigger, `tool.<name>` (generic wrapper over **any** registry tool — RSS/read_url/weather/kb_search/python_exec/MCP/custom, zero new code per node), `if` (branch), `set` (field mapping). **Expression resolver** (`expression_resolver.py`, standalone + unit-tested, **AST-walked, no `eval`/`exec`**) resolves each param by dispatch: `={{ ... }}` → sync **mini-resolver** (navigate `$node.<id>.output.<path>`, `$json`, `$trigger`, `$env`, `$now`; whitelisted funcs `default`/`upper`/`lower`/`len`/`join`/`slice`/`first`/`last`/`get`/… + operators, comparisons, ternary) covering ~90% of cases, native type preserved for a single pure expression, string interpolation for mixed text; `=py: ...` → **escape hatch** into the existing `python_exec` sandbox with a read-only `ctx` for real logic (list-comprehensions etc.); anything else is a literal. The engine calls `await resolve_params(node.params, ctx)` immediately before each node — a single, testable point. REST (kept **separate** from the Phase 18 agent runs at `/v1/workflows`, mounted at **`/v1/graph-workflows`**): `GET /node-types` (palette catalog), `GET/POST/PATCH/DELETE /` (CRUD + auto-versioning, audited), `POST /{id}/run` (body = trigger payload), `POST /{id}/activate|deactivate`, `GET /{id}/runs`, `GET /{id}/versions` + `POST /{id}/versions/{v}/restore`, `GET /runs/{rid}` (+ node_runs), `GET /runs/{rid}/stream` (SSE live, reuses the notification-stream pattern).
- **29.b — Triggers** ✓ — `schedule` (cron/RRULE/NL via `reminder_parsing`, fired from the `reminder_service`-style polling loop in `workflow_graph_service.start_scheduler()` with `next_run_at` recompute — **absorbs Phase 27**), `webhook` (`POST /v1/wf/hooks/{token}`, public + token-scoped, JSON body becomes `$trigger`), `event` (`dispatch_event()` fires active workflows subscribed to an internal event). Enable/pause + delete per trigger; manual "run now".
- **29.c — Visual canvas** ✓ — Angular editor on a new **`/graph-workflows`** page (`graph-workflow-page.component`): dependency-free **SVG canvas** with draggable nodes, bézier connections and click-to-connect output→input handles; a categorised **node palette** (triggers/actions/logic/data/ai, tool nodes generated from `/node-types`); a per-node **inspector** rendering each type's `params_schema` (text/number/expression/json/code fields, retry + continueOnFail); a **run & triggers panel** that consumes the 29.a SSE and colours nodes live (running/ok/error/skipped) and manages schedule/webhook triggers; save/activate/version. Five-locale labels (en/it/es/fr/de).
- **29.d — Flow richness** ✓ — `switch`/`merge`/`for`/`repeat` control nodes (the `for`/`repeat` loop nodes run a body subgraph once per array item / N times with `$item`/`$index` in scope, collecting `{items, count}` on the `done` handle) and `filter`/`code` (sandbox) data nodes, `llm.completion` (single provider call) and `llm.agent` (bridge node running the Phase 18 agent loop over the full tool registry — built-in + MCP + custom — to completion), immutable version history + rollback. AI nodes use a reusable model picker mirroring the chat filters; the palette exposes discovered MCP + custom tools (two-level collapse). (`splitInBatches` fan-out and the per-run cost rollup remain future extensions; delivery is available today via `tool.create_reminder`/notification tools.)

## Phase 37 — Pluggable persistence (SQLAlchemy Core) + parallel Data Access Service
*Today all persistence is raw `aiosqlite`: 24 repositories with ~472 SQLite-specific `?` placeholders, DDL as one `_SCHEMA` string, hand-rolled `_migrate_*` functions, and engine-bound features (FTS5, `vec0`/sqlite-vec, `INSERT OR REPLACE`, `PRAGMA`, `AUTOINCREMENT`). This phase decouples the repositories from the SQL dialect behind a **SQLAlchemy Core async facade**, makes the relational engine swappable (SQLite / PostgreSQL / MariaDB / Oracle) selected by a single `DATABASE_URL`, and lets the whole persistence layer be extracted into a **parallel Data Access Service** toggled by a flag — in-process at zero latency by default. Reuse-first: the abstraction seam introduced in 37.a turns the move to a separate service into a transport swap, not a rewrite. **Vector + full-text search deliberately stay on the existing sqlite-vec/fts5 retrieval store on every engine** (37.d) — the hardest, most engine-specific part is kept out of scope. SQLite remains the default throughout, so nothing breaks for existing deployments.*

- **37.a — Persistence facade + SQLAlchemy Core migration (SQLite parity, zero behavior change)** — new `app/db/engine.py` builds an `AsyncEngine` from `DATABASE_URL` (default `sqlite+aiosqlite:///…`, back-compat from `db_path`), with per-engine pooling. `get_db()` stops yielding an `aiosqlite.Connection` and returns a `Db` wrapper (protocol: `execute`/`fetchone`/`fetchall`/`commit`) over an `AsyncConnection`, so the 24 repositories' signatures change **mechanically, not structurally**. The `_SCHEMA` string becomes dialect-neutral `MetaData`/`Table` Core definitions (epoch `Integer` timestamps, JSON as `Text`, abstracted booleans) → single source of truth for every engine. The 472 `?` queries rewritten (`text()` with `:named` params for the trivial ones, Core constructs for upsert/dialect-sensitive ones). **The existing test suite passes unchanged on SQLite.** This is the one-time, highest-risk lift — done only against a green suite.
- **37.b — Alembic + dialect-aware schema** — replaces the hand-rolled `_migrate_*` and `CREATE TABLE IF NOT EXISTS` bootstrap with **Alembic** (autogenerate from the Core metadata). A baseline migration captures the current schema; existing SQLite files are stamped to the baseline on first boot (idempotent, no data loss). Per-dialect DDL variance via `.with_variant()` (Oracle booleans, MariaDB index-length caps, etc.).
- **37.c — Engine drivers: PostgreSQL, MariaDB, Oracle** — async drivers behind extras: `asyncpg` (`postgresql+asyncpg`), `asyncmy`/`aiomysql` (`mysql+asyncmy` → MariaDB), `python-oracledb` async (`oracle+oracledb`), selected purely by the `DATABASE_URL` scheme. Per-engine pool tuning (`pool_size`, `max_overflow`, `pool_pre_ping`). The `PRAGMA journal_mode=WAL`/`foreign_keys` and admin seeding move behind a dialect check (SQLite-only). Covers **relational tables only** — no native vector/FTS index work. Docker compose profiles `--profile postgres|mariadb|oracle` spin the engine and re-run **the same** suite in Docker (host Python too old → Docker).
- **37.d — Retrieval store: vector + FTS always on sqlite-vec/fts5 (unchanged)** — vector and full-text search do **not** follow the relational engine: `kb_chunks` + embeddings + the `vec0` ANN index + `fts5` stay on a **dedicated SQLite retrieval store** (today's code — `knn_chunks` ANN + numpy fallback + FTS — untouched), always a local file alongside the primary engine. When `DATABASE_URL` points at PostgreSQL/MariaDB/Oracle, the *relational* persistence migrates to the chosen engine — **including `kb_documents` metadata + canonical markdown** (one authoritative place for document metadata) — while only chunks/vectors/FTS live on the SQLite sidecar. The 37.a facade routes KB retrieval ops to the retrieval store (`RETRIEVAL_DB_URL`, default = local SQLite file) and everything else to the primary engine; `RAG_USE_SQLITE_VEC` + the numpy degrade remain the universal fallback. Zero retrieval rewrite, no ANN perf regression, no dependency on per-DB vector extensions.
- **37.e — parallel Data Access Service (opt-in topology)** — the facade wrapped in a standalone `data-access-service` process (internal FastAPI/gRPC) that owns the pool and is the only thing talking to the engine, with its own Dockerfile + compose service. The backend gets `PERSISTENCE_MODE=embedded|service`: `embedded` (default) keeps repos in-process (today's behavior, zero latency); `service` swaps the `Db` wrapper for a **remote client** that RPCs the DAS — a transport swap thanks to 37.a's `Db` protocol. Internal auth (service token), health/readiness, connection draining; the Telegram bot + workflow engine inherit it for free (shared repos). The SQLite retrieval store stays local to the DAS/backend so no vectors cross the wire per KNN. Trade-off documented: service mode = independent scaling/isolation at the cost of a network hop and cross-repo transaction boundaries (mitigation: keep multi-statement txns inside a single DAS call).
- **37.f — Data migration tooling, config & docs** — `sibyl-db migrate --from sqlite://… --to postgresql://…`: engine-agnostic export/import of the **relational** tables (streamed in FK order) on top of the existing backup/export tooling, **leaving the SQLite KB store intact** (no re-embed needed). Config surface: `DATABASE_URL`, `RETRIEVAL_DB_URL`, `PERSISTENCE_MODE`, `DATA_SERVICE_URL`, pool knobs; `/info` + `/health` report the active engine + pool stats. `docs/persistence.md` (engine matrix, embedded-vs-service topology, migration guide), README index entry, five-locale labels for the admin surface showing the active engine.
